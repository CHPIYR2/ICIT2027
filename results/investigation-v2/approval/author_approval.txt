# Author Approval — Command-Target Amendment

The command-target feasibility result is approved.

The investigation-specific static command-address mapping may now be implemented under a new versioned evidence/export contract.

The previous classification evidence contract, classifiers, features, models, and results must remain unchanged.

## 1. Approved interpretation

For the actually observed and audited Sherlock command types:

```text id="2gkq76"
45
47
50
```

the investigation system may parse command object addresses and map:

```text id="lyzh95"
CA + IOA
→ static CONFIGURATION control point
→ opaque mapped asset
```

using only the approved static mapping fields.

Do not claim evaluated support for ASDU types 46/48/49/51 unless separately audited later.

No need to expand to those types for the current paper.

# 3. Required schema correction

Before implementation proceeds, update every relevant evidence-ID namespace to support:

```text id="upwkeu"
a_[0-9a-f]{24}
```

The current proposed investigation claim schema still excludes this namespace in several locations.

Audit and update at minimum:

```text id="1f5z6g"
claim.evidence_ids
command payload
asset relationship record IDs
temporal association earlier/later IDs
verification schema
retrieval schema
visibility receipts
cross-field validators
tests
```

Do not merely broaden all IDs blindly.

Only fields that may legitimately reference a command-address observation should accept `a_`.

Add tests ensuring illegal evidence namespaces remain rejected.

---

# 4. Amend command_observed policy

Support two strengths.

## Without valid address mapping

Allowed:

> A command-type activation request was observed.

Not allowed:

```text id="9bxwh2"
target asset
execution
physical success
causation
malicious intent
```

## With exact_static_match address evidence

Allowed:

> A command-type activation request addressed to a control point mapped to asset X was observed.

Required evidence:

```text id="1fy45p"
command message evidence
command-address evidence
static mapping evidence
```

Still not allowed:

```text id="zb74ca"
asset X executed the command
asset X changed because of the command
the request was malicious
the attack succeeded
```

---

# 5. Amend asset_relationship

Add:

```text id="pbvw5q"
command_address_maps_to_asset
```

This relation means only:

> A captured command address maps, via approved static metadata, to a control point associated with asset X.

It does not mean:

```text id="acqztm"
execution
physical effect
causation
compromise
```

---

# 6. Amend temporal_association

Permit `same_observed_asset` only when the verifier can establish both:

```text id="mzpnp5"
command-address → asset X
and
E channel → asset X
```

using approved static metadata.

Then the system may report capture-time ordering such as:

> A command request mapped to asset X was captured before an electrical/process observation associated with the same mapped asset.

The verifier must still prohibit causal language.

---

# 8. reported_state_change remains optional

Keep `reported_state_change` in the ontology, but:

- do not require it for event coverage;
- do not include it in minimum question sufficiency;
- do not manufacture before/after state from initial values;
- create such a claim only when two valid same-channel ordered observations with unequal boolean values exist.

A single observed state remains a `reported_value`, not a state change.

# Research boundary

The strongest cross-domain statement currently permitted is an asset-linked temporal association.

It must never be automatically upgraded into execution, causation, attack success, malicious intent, or attribution.
